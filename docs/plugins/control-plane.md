# Control plane and hot reload

This is the plan for row L of RFC 0001. It covers the management protocol, its clients and transports, the `hofundd` process boundary, live configuration reload, and the event stream. It is a design document only. No behavior or parity status changes with this document.

RFC 0001 assigns L the control crates, `/v1/hofund/*`, token-authenticated loopback and local IPC, an event stream, `apps/hofundd`, the registry-link move, `hofund serve` exec, and snapshot reload (`docs/rfc/0001-microkernel-plugins.md:695-706,776-784,843-857`). The review resolutions require `hofundd` to be the only direct registry linker and the daemon library to receive the registry as an argument (`docs/rfc/0001-microkernel-plugins.md:1097,1112-1116`). The implementation must also close the control-plane parts of feature-parity rows 11.2 and 12.3 (`docs/feature-parity.md:277,288`).

Reference citations in this plan are against yetone/magpie `dc1cfe015675e8c3529cb67b6de3c40991ef2c13`, which is newer than the RFC pin `cbbf3163cb3c87ee0c327a56bc5689ddc5eda947`. Between the two pins, these cited files changed: `internal/cli/providers_cli.go`, `internal/gateway/busy.go`, `internal/gateway/gateway.go`, `internal/gateway/oneport.go`, `internal/gui/api.go`, `internal/gui/backend.go`, `internal/gui/web.go`, `internal/middleware/middleware.go`, and `internal/settings/settings.go`. `internal/filememo/watch.go` does not exist at the RFC pin. Every other cited file is unchanged between the pins.

## Scope and non-goals

L delivers one long-running daemon that serves the model gateway and a separate management listener. The CLI uses that management API for runtime operations. `hofund serve` starts `hofundd`. Configuration changes validate and publish without interrupting in-flight model calls. Clients receive lifecycle and request-summary events.

L includes the stable DTO crate, transport client, loopback TCP, Unix domain socket, Windows named pipe, token and same-user checks, health and status, configuration editing and reload, provider and model operations, agent operations, usage, token rotation, events, and graceful shutdown. It includes the cooldown lifetime fix from issue #117 and release packaging for two CLI binaries.

The following wait for later pull requests:

- Desktop removal of its embedded daemon. RFC 0001 explicitly makes this a follower of L (`docs/rfc/0001-microkernel-plugins.md:703-706`).
- A TUI and a browser UI. They can later use the same client, but L adds neither application. A later browser UI requires a reviewed desktop-webview origin allow-list or short-lived token exchanged over an authenticated current-user channel; it must not add cookies, a wildcard origin, or an ad hoc bypass to L's browser defenses.
- An optional authentication-failure rate limit on control TCP. This is later defense in depth against log spam, not a substitute for the high-entropy bearer token.
- Socket handoff on update, feature-parity row 16.3. A management connection is not a handed-off model listener. Handoff needs listener ownership transfer, update orchestration, and drain behavior of its own (`docs/feature-parity.md:329`).
- Background-service installation, row 16.4, including systemd and launchd integration (`docs/feature-parity.md:330`).
- Full routing-history, quota-history, request-body capture, profiling, named gateway keys, and service-management APIs. Request summaries and cooldown events are the L subset, not those later surfaces.
- The `apps/cli` mechanical move. It stays in row J, after L and I, as RFC 0001 already orders it (`docs/rfc/0001-microkernel-plugins.md:745,856-857`). Moving it in L would mix process changes with a tree-wide mechanical move.

### Listener, token, router, and models

The default model listener is `127.0.0.1:3425`; the token file defaults to `hofund.token` beside the configuration file (`crates/config/src/lib.rs:805-815`; `crates/daemon/src/lib.rs:789-798`). Startup loads the configuration, creates or reads the token, opens usage and model state, builds the router and gateway, binds the configured `SocketAddr`, and starts model refresh (`crates/daemon/src/lib.rs:204-235`). `Gateway::bind` uses a Tokio `TcpListener` and `axum::serve` with graceful shutdown (`crates/gateway/src/lib.rs:176-203`).

The gateway's `/health` route is unauthenticated. Other model and inbound-surface routes require authentication (`crates/gateway/src/lib.rs:143-174,240-256,350-356`). Authentication accepts Bearer, `x-api-key`, `x-goog-api-key`, or a query key and compares each presented value in constant time (`crates/gateway/src/lib.rs:525-538,557-607`). With a token file, every request re-reads it; an unreadable or empty file leaves the last good token in force (`crates/gateway/src/lib.rs:96-109,541-555`). Rotation writes and syncs a temporary mode-`0600` file on Unix and renames it over the old file (`crates/secrets/src/lib.rs:102-113,126-169`).

`router()` currently creates a new `Arc<Cooldowns>` on every invocation, builds providers with that book, and passes it to membership (`crates/daemon/src/lib.rs:268-314`). Membership stores the book in its table and injects the same `Arc` into every router it publishes (`crates/daemon/src/membership.rs:45-50,146-160,205-226`). The `Snapshot` wraps `ArcSwap<Router>`; each request keeps the `Arc<Router>` it loaded, so a store does not alter that request's router (`crates/router/src/snapshot.rs:14-20,46-58`). There is no configuration reload today; the architecture document reserves it for L and distinguishes token-file re-reads from configuration reload (`docs/architecture.md:234-243`).

`ModelsHost` already owns configured-instance registration, persistent model state, list aggregation, and probes (`crates/daemon/src/models.rs:166-220`). Its `list_models` and `probe` methods are async host operations, and probe refreshes the list before selection (`crates/daemon/src/models.rs:433-517`). L exposes these operations through control calls; it does not put listing or probing in the client.

## Protocol

### Versioning and DTO rules

Every management path starts `/v1/hofund`. JSON request and response bodies carry `"version": 1`; query-only and empty requests use the path version. `hofund-control-proto` exports `API_VERSION: u32 = 1`. A mismatched version is an explicit protocol error, not a best-effort decode.

Public DTOs use serde and `#[non_exhaustive]`. Requests reject unknown fields so a typo cannot change meaning. Responses permit unknown fields so an older client can read a newer compatible server. Optional response fields are additive. Enum consumers match a wildcard; response enums that serde must decode include an `Unknown` fallback. The control wire uses snake_case field and enum names; `/v1/hofund/*` is a new client API that replaces the reference GUI's `/api/*` handler (camelCase) and is intentionally not wire-compatible with it.

```rust
pub const API_VERSION: u32 = 1;

#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
#[serde(deny_unknown_fields)]
pub struct ConfigApplyRequest {
    pub version: u32,
    pub expected_revision: String,
    pub text: String,
}

#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
pub struct ConfigResponse {
    pub version: u32,
    pub disk_revision: String,
    pub runtime_revision: String,
    pub generation: u64,
    pub text: String,
    pub pending_restart: Vec<String>,
    pub not_applied: Vec<FieldIssue>,
}

#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
#[serde(deny_unknown_fields)]
pub struct PicksSetRequest {
    pub version: u32,
    pub expected_picks_revision: String,
    pub ids: Option<Vec<String>>,
    pub edit: Option<Vec<String>>,
}

#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
pub struct PicksResponse {
    pub version: u32,
    pub picks: Vec<String>,
    pub picked_from: Vec<String>,
    pub delisted: Vec<String>,
    pub picks_revision: String,
}

#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
pub struct ErrorEnvelope {
    pub version: u32,
    pub error: ControlError,
}

#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
pub struct ControlError {
    pub kind: ControlErrorKind,
    pub message: String,
    pub request_id: String,
    pub retry_after_ms: Option<u64>,
    pub details: Vec<FieldIssue>,
}

#[derive(Clone, Copy, Debug, serde::Serialize, serde::Deserialize)]
#[non_exhaustive]
#[serde(rename_all = "snake_case")]
pub enum ControlErrorKind {
    Unauthorized,
    Forbidden,
    NotFound,
    MethodNotAllowed,
    Conflict,
    InvalidConfig,
    Unavailable,
    Upstream,
    Timeout,
    Internal,
    #[serde(other)]
    Unknown,
}
```

Times on the wire are Unix milliseconds. Durations such as retry hints are unsigned milliseconds. A cooldown's monotonic `Instant` is converted to a remaining duration or wall-clock deadline by the server; neither `Instant` nor `Duration` appears in the proto. Text limits are explicit: configuration bodies at most 1 MiB, error messages at most 4 KiB, and request IDs bounded ASCII.

Decode diagnostics echo a client-chosen field name only when it is 1-64 bytes of `[A-Za-z0-9_]`; other keys fall back to `body`, and values are never echoed. Response decoding rejects event boot ids outside the composite-id grammar and known payload/topic mismatches while preserving unknown-event forward compatibility. Error envelopes reject oversized messages or detail text, invalid request ids, and more than `MAX_IDS` details rather than silently truncating or replacing wire content.

The proto crate starts at 0.1.0. Before 1.0, additive DTO or event changes are patch releases and breaking changes require a minor release plus a new `/vN` route. After 1.0, those categories become minor and major respectively. The server and client check both path and body versions. CI keeps a public-API snapshot and committed JSON snapshots for every DTO and event.

Issue #121 concerns the public plugin and cooldown Rust types. The control protocol does not re-export or serialize `ProviderErrorKind`, `ProviderError`, `CooldownPolicy`, `CooldownCause`, or plugin-api types. It maps failures to `ControlErrorKind`, optional HTTP status, retry milliseconds, and a sanitized message. Cooldown status uses a separate non-exhaustive wire enum and stable member id string. Issue #121 still needs its own Rust API decision; L does not resolve it by leaking those types into another public crate.

There is deliberately no control `token show` route. Local `token show` reads the same file through config and secrets. `ConfigResponse.text` is the full TOML because L edits whole documents; it can contain credentials and is returned only over an authenticated current-user channel. It is never included in events, logs, status, or error details. A config revision is the SHA-256 content hash of the on-disk file. `StatusResponse`, `ConfigResponse`, and the snapshot event all expose `disk_revision`, `runtime_revision`, `pending_restart`, and `not_applied`; unequal revisions mean drift, while pending fields name restart-only configuration written to disk but not yet active and not-applied issues name live fields whose runtime update failed. Errors use 400 for malformed requests, 401 for authentication, 403 for peer, Host, or Origin refusal, 404 for unknown ids, 409 for disk-revision, stale-plan, and stale-picks-revision conflicts, 422 for validation, 429 only when an upstream supplied that result, 500 for internal failures, and 503 when the daemon is stopping or unavailable. Restart-only differences are not conflicts: a successful apply records them in `pending_restart`. An apply whose only failure is model relisten returns 200 with `not_applied` containing a `listen` field issue and the sanitized bind error; the rest of the candidate remains published.

`PicksSetRequest` has exactly one of `ids` or `edit`. A nonempty `ids` list replaces the full pick list; an empty `ids` list returns 422. An `edit` list contains only `+a` and `-b` changes, or is the single token `all` or `-` to restore the default list; mixing full ids and changes is invalid. An edit that leaves no picks is an error because an empty pick list means the default, not no models. The reference forms are `editPicks` (`internal/cli/providers_cli.go:1894-1940`). The `none` form is deferred until host state has a distinct no-models flag; L returns 422 for it rather than silently exposing the default list. `none` is recognized only when it is the sole whole argument (`ids == ["none"]` or `edit == ["none"]`), so until the flag lands a model literally named `none` cannot be picked. `PicksResponse` exposes the current `picks`, `picked_from`, and `delisted` state from `ModelsHost::picks`, and writes go through a new revision-checked `ModelsHost` method that L5 adds (`crates/daemon/src/models.rs:112-137,222-247`). The current `set_picks` takes the state mutex internally, takes no revision, and returns `()`, and `picks` locks separately, so a GET-hash-then-`set_picks` sequence is not atomic. The new method holds the state mutex across load, revision compute, compare, apply, and save, and returns either the new revision or an error. Picks never touch the TOML config file.

`picks_revision` is the SHA-256 of the canonical serialized in-memory `ProviderState` (the `serde_json::to_vec_pretty` bytes that `save_state` writes; its `BTreeMap`s keep the bytes deterministic, so daemon and one-shot agree), not a hash of the file on disk. After a successful save it equals the hash of the persistent host-state file under `.hofund/host/models/`; the existing filename includes the provider slug and id hash, and state writes already use a synced temporary file, rename, and directory sync (`crates/daemon/src/models_state.rs:288-335`). The server loads or initializes default state before returning its revision. GET and PUT picks and model refresh serialize on the `ModelsHost` state mutex. PUT rereads the state under that mutex and returns 409 when `expected_picks_revision` is stale, without applying the edit. A successful response returns the new content revision. A failed save, or a provider whose existing state file belongs to another id, returns 500 and never reports success with a stale or absent revision. This changes current behavior in L5: `StateStore::update` and `save` log a warning and continue when the write fails or the file is mismatched (`crates/daemon/src/models_state.rs:36-75`), so L5 makes the save result propagate to the picks method instead of being swallowed; `picks_route_save_failure_returns_500_without_revision` covers it.

## Transports and discovery

### Separate loopback listener

Use a separate control listener. Do not mount `/v1/hofund/*` on the model gateway. The model listener accepts any configured `SocketAddr` today (`crates/config/src/lib.rs:23-29,447-455`), while management must never follow it onto a LAN. Separate listeners also keep model authentication's query-key compatibility away from management and allow management Host and Origin rules to be strict.

The default control TCP address is `127.0.0.1:3426`; an explicit IPv6 choice is `[::1]:3426`. Startup rejects every non-loopback control address. On Unix, the default is the per-config Unix socket, with TCP enabled only when configured or when the socket cannot be used. Windows prefers the named pipe with the same TCP fallback. A single daemon may enable both for migration and testing. The model gateway can still bind a LAN address without exposing a management route.

Use Tokio `TcpListener` and `UnixListener` and `tokio::net::windows::named_pipe` for I/O. Axum routes requests; hyper serves accepted socket and pipe streams through hyper-util's IO adapter. The client uses hyper HTTP/1 connections over the same three stream types. No new heavyweight transport framework is justified.

### Unix socket

Resolve the configuration with `canonicalize()`, including symlink resolution, then derive `id` as the first 16 lowercase hexadecimal characters of SHA-256 of its UTF-8 bytes. On case-insensitive filesystems, case-normalize the canonical path before hashing. The socket filename is `control-<id>.sock`, so path spelling cannot create two identities for one configuration.

1. When `XDG_RUNTIME_DIR` is absolute and owned by the current user, use `$XDG_RUNTIME_DIR/hofund/control-<id>.sock`.
2. Otherwise use `/tmp/hofund-<uid>/control-<id>.sock`, including as the short macOS fallback. Create the hofund directory mode `0700` and the socket mode `0600` through std permission APIs.
3. Reject a path whose parent is a symlink, has the wrong owner, or is group/world accessible. Never unlink a live or non-socket path. Fail when the platform socket-path limit would be exceeded rather than silently choosing a less predictable location.

### Cross-process locks and discovery

The single-instance lock is `.hofund/daemon-<id>.lock` and the discovery file is `.hofund/control-<id>.json`, both primarily beside the resolved config. Thus two config files in one directory have independent daemons and discovery. Before the stale-socket check, the daemon takes its exclusive advisory lock and holds it for the daemon's lifetime. Only the lock holder may probe and remove a stale socket after a connection fails. A second start leaves the socket alone and reports `already served by PID n` from discovery, matching the identity purpose of the reference's `ServedBy` probe (`internal/gateway/gateway.go:293-341`).

All advisory locks use std `File::lock` and `File::try_lock`, stable since Rust 1.89 and available under the workspace's Rust 1.99.1 minimum (`Cargo.toml:31-39`). Std uses `flock` on Unix and `LockFileEx` on Windows. If std proves insufficient, the alternative is fd-lock 4.0.4, licensed `MIT OR Apache-2.0`, with `windows-sys >=0.52, <0.60` and `rustix ^1` dependencies. The deny skip list already exempts windows-sys 0.52.0, so fd-lock can unify on it; windows-sys 0.45.0 enters only through `jni`, an Android-only dependency outside the checked graph targets. A resolve choosing windows-sys 0.59 would add a new duplicate under `multiple-versions = "deny"`, so L6's `cargo deny check` must confirm the resolution (`deny.toml:4-13,46-68`; `Cargo.lock:2297-2310,3511-3521,5297-5322`). The same mechanism locks the stable `<resolved-config>.lock` sidecar for configuration reloads and writes. That sidecar is opened and never replaced or renamed; the config file itself is never locked because atomic rename replaces its inode and a Windows lock can block the rename.

If `.hofund/` cannot be created beside a read-only config, the daemon lock and discovery file instead use the same filenames under the first available per-user runtime location, in this order: `$XDG_RUNTIME_DIR/hofund/` when that variable is set to an absolute current-user-owned path; otherwise `/tmp/hofund-<uid>/` on Unix; or `%LOCALAPPDATA%\hofund\run\` on Windows. When the config directory cannot hold `<resolved-config>.lock`, the config sidecar is `config-<id>.lock` under that same ordered runtime fallback. Reload is read-only and proceeds under this fallback lock. A config write still fails clearly, naming the read-only target directory, because its temporary file and rename require a writable directory; it never reports a partial write as success. Unix runtime directories follow the same `0700` ownership and permission rules as the socket directory. The discovery file is written atomically mode `0600` where supported and contains API version, PID, boot id, canonical config id, bound TCP endpoints if any, and socket or pipe name. It contains no token. On Unix, clients verify its file ownership and then verify the daemon with control health and authentication. Windows does not need a separate discovery-file ownership security API: the named-pipe client SID check is the ownership boundary, and authenticated loopback TCP remains the fallback.

### Windows named pipe

Use `\\.\pipe\hofund-<current-user-SID>-<config-id>` and a security descriptor equivalent to `D:P(A;;GA;;;<current-user-SID>)`. It is a protected DACL granting access only to the current user, not a default pipe ACL. The server also verifies the connected client's SID before the first HTTP request.

Tokio named-pipe APIs cover pipe I/O, but creating that ACL and checking a client SID requires Windows security APIs. L1's platform spike is Windows-only. Prefer a maintained safe crate with both exact capabilities. If none suffices, use one isolated `hofund-platform-win` crate with a narrow audited `unsafe_code` allowance, a `SAFETY` comment on every unsafe block, an invariant test proving no other crate opts out of the workspace `forbid` rule, and Windows CI (`Cargo.toml:65-67`). Windows stays on authenticated loopback TCP until that support lands; it never uses a default ACL. Until the pipe lands, the Windows token file is protected by the current user's profile-directory ACL because the existing atomic writer sets mode `0600` only on Unix (`crates/secrets/src/lib.rs:126-169`).

### Client discovery order

1. An explicit `--control` endpoint or `HOFUND_CONTROL`, for tests and advanced setups. Only numeric loopback TCP, the expected Unix socket scheme, or the expected Windows pipe scheme is accepted.
2. `.hofund/control-<id>.json` beside the resolved config, checking API version, config id, the platform ownership rule above, and then control health.
3. The same discovery filename under the runtime locations in the daemon's order: valid `$XDG_RUNTIME_DIR/hofund/`, then `/tmp/hofund-<uid>/` on Unix or `%LOCALAPPDATA%\hofund\run\` on Windows.
4. The computed per-config Unix socket or Windows named pipe.
5. The configured control TCP address, defaulting to `127.0.0.1:3426`.

Each failure falls through only for connection refusal, not for a wrong token, wrong protocol version, Host refusal, or wrong peer. Those are actionable errors and trying another endpoint could hide a security problem.

## Authentication and browser-request defenses

Use the same `TokenFile` as the model gateway. TCP requires exactly `Authorization: Bearer <token>`; query tokens and the model gateway's alternate API-key headers are not accepted. Re-read the token file on each request and compare in constant time, preserving the current last-good behavior on an unreadable or empty file (`crates/gateway/src/lib.rs:541-555,596-607`). Never derive or print a `Debug` containing a token, put it in a URL, or include it in tracing, errors, discovery files, SSE, or DTO snapshots.

Require both bearer authentication and a same-user peer check on Unix sockets and Windows pipes. Unix uses Tokio `UnixStream::peer_cred` and std permissions, with no FFI or unsafe code; L4's Unix half is therefore not blocked by the Windows decision. Windows uses the pipe client SID. Peer lookup failure closes the connection. These checks complement, rather than replace, the 0600 socket, 0700 directory, and current-user pipe ACL.

Rotation calls the existing atomic replacement operation (`crates/secrets/src/lib.rs:102-113,126-169`). The rotation request and agent-file updates complete before the response returns the new token. Subsequent model and control requests require it; old tokens fail. Existing SSE connections close with a `token_rotated` control event and reconnect using the new token. A token file changed outside the daemon takes effect on the next ordinary request, as it does today. Every SSE connection also re-reads the token on its 15-second heartbeat and closes when the token changes, so an external rotation cannot leave an indefinitely authorized stream. A token-path change is written with `pending_restart`; until restart, rotation and re-reads continue using the running path.

Control TCP is loopback-only even when the model gateway binds a LAN address. Apply these HTTP checks before routing:

- `Host` must be the exact numeric loopback host and bound port used by the listener, including `[::1]:port` for an IPv6 listener. Reject DNS names, including `localhost`, so DNS rebinding cannot turn a browser into a management client.
- Do not emit CORS permission headers. Reject a cross-site `Origin`; accept only an exactly matching numeric-loopback origin when one is present, including the IPv6 form. CLI and native clients omit Origin. A later webview origin needs an explicit reviewed allow-list entry, not a wildcard.
- Over a Unix socket or named pipe, the client sends the constant `Host: hofund-control`; the server pins that value rather than applying the TCP numeric-loopback rule.
- Mutations require `Content-Type: application/json` and a bounded body. Form posts and simple cross-origin content types are rejected. Authentication is never cookie-based.

## Event stream

Use SSE, not WebSocket or NDJSON. SSE already matches HTTP, needs no upgrade or additional locked crate, supports `Last-Event-ID`, and is sufficient for one-way daemon-to-client updates. Each frame has a composite id containing every subscribed topic's cursor, an event name, and one JSON `EventEnvelope`. For example, a two-topic frame has `id: <boot-id>:control=12,requests=40`, including when its payload belongs to only one topic. A comment heartbeat is sent every 15 seconds. Every event contains API version, boot id, topic, per-topic sequence, Unix-millisecond time, and a non-exhaustive payload variant.

| Event | Payload and use |
| --- | --- |
| `snapshot` | Current status, disk and runtime revisions, generation, pending-restart and not-applied fields, provider/member summary, and latest cursor for each requested topic. Sent first on every connection. |
| `config_reloaded` | New disk and runtime revisions and generation, changed member ids, `pending_restart`, and `not_applied`. No TOML or secrets. |
| `config_rejected` | Sanitized field issues and rejected revision. The old generation and last good runtime snapshot remain. |
| `listener_relisten_failed` | The `listen` field issue, sanitized bind error, retained running address, and current revisions and generation. The rest of the candidate remains published. |
| `member_cooled` | Member id, stable wire cause, retry or remaining milliseconds, and failure count. No ProviderError or policy type. |
| `member_recovered` | Member id and new readiness. |
| `snapshot_published` | New generation and route/member counts. Panic-driven publication uses this too. |
| `request_started` | Request id, route id, inbound protocol, and start time. No body, headers, URL query, or credential. |
| `request_finished` | Request id, selected member when known, status class, duration, and token counts when known. This is the usage-event subset of rows 11.2 and 12.3, not request capture. |
| `models_refreshed` | Provider id, list kind, model count, success or sanitized failure. |
| `agent_changed` | Agent id, action, changed paths, and warnings without token material. |
| `sign_in_progress` | Reserved additive event for H; no L producer is required. |
| `token_rotated` | Notification only; clients reconnect with the new token. |
| `shutdown_started` | Drain state. |
| `resync_required` | Affected topic and current per-topic snapshot after lag, unknown boot id, or an unreplayable Last-Event-ID. |

The `control` and `requests` topics have separate bounded Tokio broadcast channels, separate replay rings, and independent sequence spaces. A client requesting `?topics=control,requests` receives both streams on one SSE response. Before taking the snapshot, the server subscribes to every requested topic; after sending the snapshot, it drops buffered events at or below that topic's snapshot cursor. This ordering closes the snapshot/subscribe gap without duplicates. Each broadcast holds 4,096 events and each ring retains at most 4,096 serialized events and 4 MiB, evicting oldest entries until both limits hold. Slow clients never block producers or other clients. `Lagged` on one topic emits `resync_required` and a fresh snapshot only for that topic, and the client discards only that topic's derived state. Request traffic therefore cannot lag or evict control events. There is no unbounded per-client queue.

`request_started` and `request_finished` are excluded from the default `control` topic and emitted only for clients requesting `?topics=requests` or `?topics=control,requests`. At 100 requests per second, the two request events per request fill the request topic's event-count window in about 20 seconds without shortening control retention. The L6 load test exercises this rate with a slow subscriber and both per-topic caps.

The exact frame-id grammar is `boot-id ":" cursor ("," cursor)*`, where `cursor = topic "=" sequence`. `boot-id` is nonempty ASCII excluding `:`, `,`, `=`, and whitespace; `topic` is `control` or `requests`; and `sequence` is an unsigned decimal integer with no leading zeros except `0` itself. Cursors appear in canonical topic order `control`, then `requests`, exactly once each. Every emitted frame carries the latest delivered cursor for every subscribed topic, so a standard EventSource reconnect sends enough state in one `Last-Event-ID` to resume all topics. A matching retained cursor resumes its topic after that sequence. An unknown boot id resynchronizes every requested topic. A topic missing from an otherwise valid id resynchronizes only that topic; a cursor older than its topic's retention does the same. A duplicate cursor or otherwise malformed id resynchronizes every requested topic, never silently losing events. Events are not persisted across daemon restarts. Raw log lines are not events in L because log redaction and volume are separate concerns. Quota history and detailed routing explanations remain later surfaces; H can add quota payloads without changing existing variants.

## Reload semantics

### Triggers and transaction

L6 supports explicit `POST /config/reload` and automatic application of external edits. A `notify` watcher watches the configuration's parent directory and, for a symlinked config, the resolved target's parent directory. It canonicalizes both every event path and the config or resolved-target path before comparing them, preserving the reference's exact-path filter while handling macOS FSEvents reporting `/private/var/...` for `/var/...` (`internal/filememo/watch.go:45-71`). Debounce runs 400 ms after the last matching event and coalesces rename and partial-save sequences; sibling events neither reset the timer nor trigger reload. This exclusion covers usage SQLite and its `-wal`/`-journal` files, token writes, `.hofund/` discovery, and temporary files, which matters because token and usage paths default beside the config (`crates/config/src/lib.rs:805-815`; `crates/daemon/src/lib.rs:789-798`). A notify overflow or rescan indication, including `Flag::Rescan` and an `Other` or need-rescan event kind, forces an immediate stat-and-revision comparison and reload check because its path list may be incomplete. If watcher setup fails or the watcher terminates, a 2 s stat-polling fallback takes over. Watcher, rescan, and polling paths call the same serialized, validated reload operation. A candidate whose disk content revision equals the runtime revision is skipped, which also absorbs the daemon's own apply writes. An invalid edit emits `config_rejected` and keeps the last good runtime snapshot. The reference likewise watches parent directories and retains a polling path (`internal/gateway/gateway.go:618-624`; `internal/filememo/watch.go:33-80`; `internal/pluginrt/config.go:363-395`), keeps a last good parsed generation (`internal/settings/settings.go:1192-1228`), and used a 2 s `KeepFresh` interval at the earlier pin (`internal/gateway/gateway.go:589`, reference `cbbf3163`). Feature-parity row 11.2 closes only when this L6 watcher and its tests land, not with explicit reload alone (`docs/feature-parity.md:277`).

`POST /config/apply` accepts a whole TOML document and an expected disk-content revision. Serialize apply, explicit reload, watcher reload, and model relisten through one async mutex. Under that mutex, re-read the disk and compare its content hash with `expected_revision`; a mismatch returns 409 and never silently overwrites a hand edit. Validation performs the same structural checks and provider construction/preflight as current `config check`, but sends no model probe (`crates/daemon/src/lib.rs:67-76`). Candidate construction happens beside the running snapshot and cannot mutate the current `ModelsHost`, event generation, refresh job, or cooldown book.

After complete validation, resolve symlinks to the real target and write the client's TOML byte-exact, without reserialization. Create and fsync the temporary file in the target's directory, preserve the symlink, copy the target's mode and owner where possible, atomically rename over the target, and fsync the directory. Apply, reload, and one-shot edits take the same exclusive `<resolved-config>.lock` sidecar lock, or the runtime `config-<id>.lock` fallback when the config directory is read-only; apply and one-shot writers hold it across the final disk-revision check and write so a cross-process writer cannot interleave. Reload needs no write and proceeds under that lock. A write into a read-only target directory fails with a clear error naming that directory before any target replacement, because the temporary file and rename cannot succeed there; the old file remains intact and no partial write is reported. A parse, preflight, file-write, or build failure returns an error, emits `config_rejected`, and leaves the old runtime snapshot in place. A failed apply also leaves the old file's last good contents untouched; a failed reload does not alter or roll back the external edit, and reports the disk/runtime drift. Publication and generation increment are infallible once the write and build succeed.

### Reloadable, live-relisten, and pending-restart fields

| Fields | Rule |
| --- | --- |
| Providers, routes, failover, subscriptions, model-list settings, endpoint and pooled-client timeouts | Reloadable. Environment-backed secrets and options are resolved again during candidate construction. |
| Model `listen` | Live in L6. One shared resolution function returns `HOFUND_ADDR` when set, otherwise config `listen`; `hofundd` and healthcheck both use it, matching the reference's environment-first `settings.GatewayAddr` (`internal/settings/settings.go:1362-1370`). Only the daemon binds this address: `hofund serve` execs the daemon and one-shot operations never bind. For a port change, bind the new address first, then close the old listener; on bind failure, keep serving on the old one. For the same port on a different host, close the old listener, bind the new one, and rebind the old address on failure. The close-first case is necessary because binding `0.0.0.0:p` while `127.0.0.1:p` listens fails with `EADDRINUSE` on Linux. In-flight requests finish on the old listener (`internal/gateway/lan.go:198-237`; `internal/gateway/gateway.go:690-704`). |
| `token_file` | Write with `pending_restart: ["token_file"]`. Token contents at the running path remain live without reload. |
| `usage_file` | Write with `pending_restart`. Moving an open ledger mid-request needs a separate ownership design. |
| Control listener, socket, pipe, and discovery settings | Write with `pending_restart`. |
| Plugin registry contents, compiled agent descriptions, and inbound surfaces returned by `hofund_plugin_registry::surfaces()` | Write with `pending_restart`; registry and surface changes normally require a new binary rather than TOML reload. Surfaces are currently attached at startup (`crates/daemon/src/lib.rs:204-227`). |

Apply validates, writes, publishes, and then relistens under the same mutex; it cannot pre-bind a same-port host change. When `HOFUND_ADDR` is set, a config `listen` change publishes but does not relisten: the environment wins, and the response reports `not_applied` with a `listen` issue whose reason is `env_override`. Otherwise, a relisten bind failure does not reject the rest of the candidate: apply or reload still publishes it, keeps or restores the old listener, returns `not_applied` with a `listen` issue and bind error, and emits `listener_relisten_failed` in addition to `config_reloaded`. If restoring the old address also fails, the daemon logs the fatal error through its error-tolerant writer and exits non-zero so its supervisor restarts it. While the running listener differs from the effective address, `listen` remains in `not_applied`, not `pending_restart`. Status exposes the configured, effective, and running addresses and whether the effective address came from `environment` or `config`. While `HOFUND_ADDR` overrides `listen` and the configured `listen` differs from it, status and snapshots keep reporting `listen` in `not_applied` with reason `env_override`, including after a startup whose config `listen` already differed. An explicit `config reload` retries relisten even when disk and runtime revisions match, except when the environment override applies; the watcher's equal-revision skip does not retry it.

For every pending-restart row, apply and reload publish all reloadable changes and retain the old runtime resource for the named fields. On every publish, recompute `pending_restart` as the diff between the running immutable restart-only settings and the current published config rather than accumulating field names; reverting an edit therefore clears it on the next publish. `StatusResponse`, `config_reloaded`, and `snapshot` expose that recomputed set, and none of these differences returns a restart-required conflict. `runtime_revision` identifies the last published config generation, so a successful apply with pending fields or a relisten failure leaves disk and runtime revisions equal; `not_applied` distinguishes the latter. Drift means an unapplied or rejected disk edit, not a pending restart. After restart the pending set is empty.

In-flight requests retain their old `Arc<Router>` and its owned membership table; new requests load the new ArcSwap snapshot (`crates/router/src/snapshot.rs:46-58`). L6 reuses a plugin instance when its canonical build fingerprint is unchanged. That fingerprint is a domain-separated SHA-256 hash of the canonical provider configuration section and resolved secret inputs; neither secret material nor a reversible encoding appears in it. Reuse preserves instance-held learned state such as Mantle's `LearnedRoutes` (`crates/provider/src/mantle.rs:20-25`), whose reference counterpart is process-level learned route state (`internal/gateway/mantle.go:30-36`). Changed instances are rebuilt. Retired instances receive one bounded asynchronous `shutdown` only after the last old `Arc<Router>` drops, so a long stream spanning reload finishes normally.

Stable `MemberId` values, not vector positions, carry cooldown identity across reload. Moving the same provider between routes preserves its id; renaming a provider creates a new id and allows the old entry to be pruned. Each member also has a hashed provider configuration fingerprint covering credentials and `base_url`. On successful reload, clear that member's cooldown entry when the fingerprint changes, so a new key or endpoint starts fresh while unchanged members retain state; never store clear secret material in the fingerprint. This extends the reference's credential-sensitive rest identity (`internal/provider/keys.go:68-85`). The candidate membership table and all its published routers receive the existing shared book. Model refresh state remains host-owned and persistent, while the refresh loop is replaced with the candidate's timing and reused or rebuilt instances.

## Issue #117 and cooldown lifetime

Issue #117 is a prerequisite inside L, not a follow-up. Hoist `Arc<Cooldowns>` out of `router()` into the daemon runtime state before reload lands. Every startup, reload, panic publication, and recovery publication uses that one book. Today only membership republishes share it; a second `router()` call would create a fresh book (`crates/daemon/src/lib.rs:268-285`; `crates/daemon/src/membership.rs:205-226`).

Pruning follows these rules:

1. After a successful reload, remove entries whose `MemberId` is absent from the candidate. Never prune on rejected validation.
2. Success never inserts a missing entry. `record_success` and `record_success_if_unchanged` currently call `states.entry(...).or_default()` (`crates/router/src/cooldown.rs:228-260`); change them to mutate only an existing entry and remove it when the clear leaves no ladder history. Preserve the revision guard by drawing revisions from one book-wide monotonic counter instead of a per-entry counter. The counter starts at 1; 0 means missing and is never assigned. `record_success_if_unchanged` treats a captured 0 with an entry now present as changed, so removal and recreation cannot let stale success clear a newer failure.
3. Prune expired idle entries on reads, outcome recording, reload, and a periodic maintenance pass. An expired rate-limit entry remains only for the configured `rate_forget` window; generic ladder history expires after the same idle interval unless a longer active rest exists. Active cooldowns are never expired by maintenance.
4. Bound the book at 10,000 entries. Evict expired entries first, then the least-recently touched idle entry. Never evict an active rest to admit an idle entry. Configured members removed on reload do not consume the budget.
5. Recovery emits `member_recovered` once when an active rest expires or is cleared, not on every read.

Issue #120 is resolved in H, not L. `QuotaObservation` now separates the HTTP retry hint from the window reset and carries the limit and credits state needed by the observation threshold. Zero remaining uses reset, retry, then default cooldowns. Positive remaining at or above the reference's general 98% used-share threshold rests only when a positive window reset is known; retry alone or no reset records nothing (reference: internal/provider/routing.go:365-375). Accounts spending credits are exempt, retry hints cap at one hour, and window resets cap at eight days. The reference's 100% exception for ordered routing remains with the strategy work in feature-parity row 4.5. L only maps already-decided cooldown state to wire DTOs.

Tests for #117 cover cooldown survival across reload and panic publication, removed-member pruning, expired-entry pruning, success against a missing id without insertion, the 10,000-entry bound, revision-guard behavior, and one recovery event per rest.

The daemon now depends on `hofund-agent`. The catalog holds adapters that are not `Send`, so each blocking call rebuilds it from the static descriptions. Closing SSE streams on rotation moves to L6, which consumes the generation watch.

**Status (L5d):** `GET /usage` maps `today`, `week`, `month`, and `all` to `hofund_usage::Window`; the first three start at local midnight, local midnight minus 6 days, and local midnight minus 29 days (`reference: internal/usage/ledger.go:198`, `internal/cli/usage_cli.go:123-136`). `Ledger::summary` computes request and token totals with one SQL aggregate over the whole period and returns at most the newest 10,000 rows, oldest first; `rows_truncated` is set when rows were dropped (the only L5 DTO change). Negative stored tokens become 0 and seconds become milliseconds. An unknown period or query key is 400 and a ledger failure is 500. `POST /shutdown` sets a watch flag and returns `{draining:true}`; a second call returns the same. `status.shutdown` then reports `draining`, and every other mutation returns 503. `serve_until_shutdown` waits for Ctrl-C or that flag and then runs the normal shutdown: the model listener drains in-flight requests, the control listener closes idle keep-alive connections gracefully, the Unix socket file is removed, and the instance lock is released. The reference flushes and exits without a drain (`reference: internal/cli/signals.go:25-70`). Embedded callers that never await the flag only see the state change (open question 7).

**Status (L6a):** `GET /v1/hofund/events` serves Server-Sent Events from a daemon `EventBus` with one bus per topic. Each topic has a broadcast channel of 4096 and a replay ring bounded by 4096 events and 4 MiB, so request traffic can neither lag nor evict control events. A subscriber takes its receivers before it reads the snapshot and drops any live frame at or below the ring position it started from, so the snapshot and the live stream never duplicate or skip an event. Event ids use the composite form `<boot>:control=N,requests=M`. `topics` defaults to `control`; `requests` is opt-in. The cursor is accepted only from the `Last-Event-ID` header, and a query cursor is 400. A cursor from another boot or a malformed one resyncs every requested topic. A topic missing from the cursor, or one older than its ring, resyncs only that topic. A lagged receiver resyncs only its own topic. Every resync is followed by a fresh snapshot. On a mixed resume, replayed frames come before the resync and snapshot, and a resyncing topic stays at 0 in event ids until its snapshot is sent, so a reconnect in between resyncs it again. The heartbeat comment is sent every 15 seconds and re-reads the token file first; a mismatch ends the stream. A live `token_rotated` (emitted once per `token_generation` change) or `shutdown_started` event is the last frame of a stream, and a subscriber that connects while draining receives the snapshot and then the end of the stream. The config read, validate, apply, and reload routes are routed and authenticated but return 503 `unavailable` until L6b. `hofund-control-client` adds the four config methods and `events`, which returns an `EventStream` with a bounded buffer that remembers the last event id for resuming.

## `hofund serve` exec and release

On Unix, `hofund serve` discovers `hofundd` beside `std::env::current_exe()` first, then searches `PATH` using the platform executable suffix. It invokes the selected path directly with `--config <path>`, inherits the environment, and uses `CommandExt::exec`. There is no shell and no parent process left to forward signals: the daemon receives them and its exit status is the command's status. `HOFUND_CONFIG` and provider `env:` values pass through unchanged; an explicit `--config` is passed exactly once.

Windows has no exec replacement. The CLI spawns `hofundd.exe`, waits, and returns the child's numeric exit code. The child stays in the same console so Ctrl-C is delivered to it; the parent waits rather than exiting ahead of graceful shutdown. A child ended without a numeric code maps to failure. A missing binary produces an actionable error naming both searched locations and the required package layout.

`hofundd` owns Tokio runtime construction, startup logging, signals, and graceful drain. Under foreground `hofund serve`, SIGHUP means terminal close: stop accepting work, drain in-flight requests, flush state, restore the signal's default disposition, and re-raise it so the supervisor sees termination by SIGHUP, not a 128-plus-signal exit (`internal/cli/signals.go:25-70`; `internal/cli/signals_unix.go:12-23`). Draining before the re-raise is an improvement over the reference, which flushes and exits without draining. As in the reference, a SIGHUP that was already ignored when the process started (`nohup`, a background job, or a service manager that ignores it) stays ignored. Otherwise daemonized mode uses the same shutdown semantics. Ctrl-C and SIGTERM also drain and re-raise on Unix. Windows has no SIGHUP and cannot re-raise a console event as a signal, so it uses Go's console-to-signal mapping and the reference's numeric-exit fallback (`internal/cli/signals.go:59-71`): Ctrl-C and Ctrl-Break drain and exit 130 (SIGINT), while close, logoff, and shutdown exit 143 (SIGTERM). Drain is best effort for close, logoff, and shutdown because Windows terminates the process about 5 s after delivering one of those events. Reload is available only through the control call and watcher; L offers no SIGHUP-as-reload or SIGUSR1 reload trigger. Drain logging uses a tracing writer that ignores stdout and stderr write errors such as `EIO` after terminal hangup, and `hofundd`'s serve path contains no `println!` or `eprintln!` that could panic while draining. The in-process `serve_blocking` remains until the CLI switch so existing desktop and CLI behavior keeps working.

Release changes are part of the switch pull request, not a later afterthought. `dist-workspace.toml` currently builds only `hofund`, and the release document says so (`dist-workspace.toml:5-37`; `docs/release.md:22-38`). The CLI archive and shell/PowerShell installers must contain both `hofund` and `hofundd` in one directory. `hofund-daemon-bin` opts into dist, macOS universal repacking includes both Mach-O binaries, checksums and signing cover both, and Windows packaging includes `hofundd.exe`. The dry-run must build actual artifacts for every release target, not only run `dist plan`, because the current process distinguishes those checks (`docs/release.md:98-121`). Desktop packaging gains no daemon sidecar in L; its later rework owns that decision.

## CLI operation without a running daemon

When ordinary discovery finds no daemon, the CLI probes the per-config daemon lock in the same order as discovery (beside the resolved config, then every runtime fallback). It opens each lock without create and never creates `.hofund/` or any other directory during this probe; a nonexistent lock file counts as not held. Only when the lock is free at every lookup location does the command follow its documented no-daemon mode below, normally one-shot `hofundd <op> --config <path>` rather than an implicitly started background service. If any lock is held but discovery is not readable yet, the CLI retries discovery with backoff for up to 5 s. If the lock is still held anywhere after that wait, the command fails and never falls back to one-shot: the error names the lock path and the daemon PID from discovery or lock metadata when present, otherwise `unknown`, and says the daemon is starting or unresponsive. `events tail` remains the explicit autostart exception; `healthcheck` directly probes the model listener instead. For one-shot operations, the CLI locates the binary by the same same-directory-then-PATH rule as `hofund serve`, passes the operation arguments exactly once, waits, and propagates its exit status. The one-shot process constructs the registry adapter, executes the operation in-process, and exits. It never takes the daemon lock, binds a listener, writes discovery, or starts the watcher. Config writes take the `<resolved-config>.lock` sidecar lock, or its runtime `config-<id>.lock` fallback, and recheck `expected_revision` before writing.

One-shot pick edits instead take the per-provider `<state-file>.lock` beside the persistent host-state file, using the same ordered runtime fallback when that directory is read-only. Under this lock the process rereads the state and expected revision, applies the full-list, delta, or reset form, computes the same in-memory revision, and writes atomically with the existing temporary-file, fsync, and rename path. A failed save or mismatched state file makes the one-shot exit non-zero and print no revision; `offline_provider_picks_save_failure_exits_nonzero` covers it. One-shot model refresh takes the same per-provider lock because refresh also writes host state. Picks never take the config sidecar or touch TOML. Thus registry linkage remains only in `hofundd`, while agent wiring, provider tests, usage, and full validation still work offline. Only `config check` has a missing-binary fallback: if `hofundd` is not installed, it may perform structural parsing but must print `structural check only; hofundd is unavailable, so provider construction and preflight did not run`. Other one-shot commands report the missing binary as an actionable error.

## Decisions

1. **Windows ACL and peer credentials — Resolved.** Unix uses safe Tokio peer credentials and std permissions. Windows prefers a maintained safe crate for the protected current-user pipe DACL and client-SID check. If none suffices, one isolated `hofund-platform-win` crate receives the narrow audited unsafe allowance, SAFETY comments, the no-other-crate invariant test, and Windows CI. Windows remains on authenticated loopback TCP until then; a default ACL is never acceptable.

   L1 outcome: the spike found no safe maintained license-compatible crate covering both operations. Windows stays on authenticated loopback TCP; L4 uses the isolated platform design and Windows CI evidence summarized in [PR L1 notes](../rfc/0001-microkernel-plugins.md#pr-l1-notes).
2. **Whole-document configuration apply — Resolved.** L uses full TOML replacement with `expected_revision` compared to the disk content hash under the serialized operation, plus the symlink-preserving, byte-exact atomic write. Cross-process writers share the stable `<resolved-config>.lock` sidecar or its runtime `config-<id>.lock` fallback, never the replaced config inode. Clients start from GET; config-backed provider edits use `toml_edit` and 409 retry rather than a second patch language. Picks are host state with their own GET/PUT protocol, content revision, and per-provider lock; they never enter this TOML path. `pending_restart` is recomputed from running restart-only settings on every publish, so reverts clear it.
3. **Automatic file watching — Resolved.** L6 watches config and resolved-target parent directories, canonicalizes both sides of exact path comparisons, debounces only matching events for 400 ms, forces stat-and-revision checks on overflow or rescan, retains the 2 s stat fallback and shared validated reload operation, skips equal-revision candidates, and keeps the last good snapshot on rejection. Row 11.2 cannot close without it.
4. **Offline `config check` — Resolved.** One-shot `hofundd check --config ...` performs full offline validation without moving registry linkage into the CLI. Structural-only validation is permitted only as a clearly labeled fallback when `hofundd` is not installed.
5. **Plugin instance reuse — Resolved.** L6 reuses instances whose canonical provider-configuration and resolved-secret fingerprint is unchanged, preserving learned state. Changed instances are rebuilt, and retired instances shut down only after their last old router reference drops.
6. **Socket handoff and background services — Resolved.** Both remain outside L. They are independent feature-parity rows 16.3 and 16.4 (`docs/feature-parity.md:329-330`); `hofundd` and the client boundary are L's only prerequisites for them.
7. **CLI removal of `hofund-agent` — Resolved.** L8 removes the CLI's daemon and agent edges only together with daemon-lock detection, bounded discovery retry, one-shot `hofundd` operations, and every named no-daemon test above. The lock must be free at every lookup location; after 5 s with any lock still held, the CLI fails with the PID or `unknown` and lock path rather than starting one-shot work. One-shot processes never take the daemon lock, bind, write discovery, or start the watcher; config writes use the sidecar lock, and picks and refresh use per-provider host-state locks. Offline reload is a successful reported no-op and offline status is a local report. Agent disconnect, provider operations backed by current config or host state, usage, and full config validation therefore keep working without a running daemon.
8. **Reference pin — Resolved.** L cites reference `dc1cfe0`; earlier rows retain `cbbf316`. The listed changed files and the explicitly marked earlier-pin citation document where behavior differs.
9. **Live relisten and listener failure — Resolved.** Port changes bind before closing; same-port host changes close first and restore on failure. Apply writes and publishes before relistening. A bind failure preserves the rest of publication and reports `listen` through `not_applied` and `listener_relisten_failed`; explicit reload retries even at equal revisions. `HOFUND_ADDR` overrides config listen for the daemon, so a config listen change does not relisten and reports `not_applied` with reason `env_override`. Failure to restore the old listener is fatal and exits non-zero for supervisor restart.
10. **Lock and discovery identity — Resolved.** Daemon lock and discovery filenames include the canonical config id, with ordered per-user runtime fallback when the config directory is read-only. Config reload and write locking uses `<resolved-config>.lock` or runtime `config-<id>.lock`; reload proceeds under the fallback, while a write into the read-only directory fails clearly without partial replacement. Std file locking supplies Unix `flock` and Windows `LockFileEx`; clients check discovery locations in the same order.
11. **Healthcheck target and address — Resolved.** The container healthcheck probes the unauthenticated model `/health` with a 3 s bound and requires 200 plus `"service":"hofund"`; it needs neither discovery nor a token. Daemon and healthcheck share `HOFUND_ADDR`-then-config resolution, and status reports the effective address and source. Unspecified IPv4 and empty hosts become `127.0.0.1`; IPv6 `[::]` becomes `[::1]` because an IPv6-only bind may not accept IPv4 loopback. Control health is optional additional diagnostics, never a substitute.
12. **SSE topic isolation — Resolved.** Control and request topics have independent broadcasts, replay rings, capacities, and sequence spaces. Every frame carries a composite `<boot-id>:control=12,requests=40`-style id with every subscribed topic's cursor in canonical order, so EventSource reconnect resumes all topics. Unknown boot ids resynchronize all requested topics, a missing topic resynchronizes only that topic, and lag resynchronizes only the affected topic.
13. **Signal termination after drain — Resolved.** Unix drains and flushes before re-raising with the default disposition, which improves on the reference without hiding signal termination from supervisors. Windows Ctrl-C and Ctrl-Break drain and exit 130; close, logoff, and shutdown exit 143, with best-effort drain under the OS's roughly 5 s termination limit. Drain logging tolerates closed stdout and stderr.
