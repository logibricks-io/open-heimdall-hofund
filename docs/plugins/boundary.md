# Plugin boundary

Plugins are in-repo Rust. A reviewer reads the diff, and the crate is linked into the `hofundd` process. `cargo xtask check-plugins` is not a sandbox. No static check can stop a determined author who is already allowed to change this repository. The gate exists so an accidental violation, and every obvious deliberate one, fails loudly in CI.

## What is enforced

`check-plugins` scans each package under `plugins/<kind>/` before it runs Cargo. It then checks `cargo metadata` target roots and the plugin target's dep-info. Only files inside that package's `src/` are lexed from the dep-info list. The three Clippy rebuild inputs named below are ignored. Every other listed path is rejected. A plugin build script is rejected in the first scan, so Cargo never runs it. The seam tests call the same pre-Cargo scan (`xtask::boundary::source_violations`).

- Direct dependencies are an allow-list: `hofund-plugin-api` and `hofund-plugin-sdk`. A dev-dependency may also be the matching kit or `tempfile`. Tokio features `full`, `net`, `process`, and `signal` are rejected. `hofund-plugin-api` and `hofund-plugin-sdk` must be `workspace = true`. A `path`, `git`, `version`, or registry spec for those crates is rejected, so a same-named crate from another path is not the workspace crate.
- `plugins/registry` is the composition crate `hofund-plugin-registry`, not a plugin. Its root `Cargo.toml` is not scanned. A nested package under that directory still fails with `plugins/registry must not contain a package`.
- The link closure is Cargo package ids, not names. It is the normal and build dependencies of the workspace `hofund-plugin-api` and `hofund-plugin-sdk`, plus the plugin itself. Dev-dependencies of those crates are not in the allowed set. Target-specific dependencies are included.
- The resolved `hofund-plugin-api` graph must not enable the `kernel` feature. `mod kernel` is private without that feature. The check follows normal dependencies (`cargo tree -e normal,features`). A dev-dependency on the plugin's own kit does not count: that kit links the host, and the host is what enables `kernel`.
- The source scan rejects `std::process`, `std::net`, `std::os::{unix,windows}::{process,net}`, `tokio::{process,net}`, and the socket and process crates named in the scan. It follows `extern crate` renames and `use` aliases, including a `use` inside a function.
- A `#[path]` that normalizes outside `src/` (the package directory for `build.rs`) is rejected. A `path` attribute nested in `cfg_attr` is rejected outright and is not followed. An in-root `#[path]` target is scanned whatever its extension.
- A macro counts as an include when its last path segment is `include`, `include_str`, or `include_bytes`, and when a `use` imports or renames one of those macros (`std::include`, `core::include`, `use std::include as sneak`). The argument must be a string literal. The path is joined to the file that contains the macro and normalized without following symlinks, and it must stay inside the package `src/` directory. Anything else is rejected: a non-literal argument (`non-literal include!`, and the same form for `include_str!` and `include_bytes!`), or a literal whose path is absolute or leaves `src/` (`include path "…" leaves src`). An `include!` that stays inside `src/` is scanned, whatever its extension. An `include_str!` or `include_bytes!` that stays inside `src/` is not opened as Rust.
- Every symlink in the plugin package is rejected, whether it is a file or a directory. The walk uses `lstat` (`symlink_metadata`) and does not follow the link. A path is classified by that unresolved location. Canonicalization is used only for the package root and the workspace root, so a macOS `/var` path and `/private/var`, or a Windows short name and its long name, still name the same directory. A symlink is not accepted because of the directory it points at.
- `cfg`, `cfg!`, and `cfg_attr` that mention `clippy` or `debug_assertions` are rejected. Before Cargo, the scan walks every `.rs` file under `src/` that is not a symlink, plus in-src `include!` targets and in-root `#[path]` targets, so a `cfg` branch this build did not compile is covered. After `cargo check` and the Clippy passes, each plugin target's dep-info (`.d`) is parsed. A plugin has no build script, so a file listed for the plugin's own target must sit inside the package `src/` directory, and that file is lexed as a token stream, whatever its extension. A listed path that is not on disk is left out; a later build can leave an older dep-info that names a file since removed. If no listed file inside `src/` is on disk, the check fails. A listed file that will not lex is rejected. A file that parses as Rust is also syn-walked. Any other listed path is rejected (`dep-info lists … outside src`). That includes the Cargo target directory, `crates/plugin-api`, `crates/plugin-sdk`, the cargo home, and the rustc sysroot. The api and sdk crates are covered by their own compilation, not by the plugin's dep-info. Clippy records three rebuild inputs that are not crate source: the workspace `Cargo.toml`, `Cargo.lock`, and `xtask/plugin-boundary/clippy.toml`. Those exact paths are ignored and not scanned. That ignore is not an include exception, and it is not an exception for a file under the target directory or under api or sdk. The lexer walks every group, whether or not the file parses as Rust. It sees a `cfg` inside a `macro_rules!` body and inside a macro argument that is not Rust. Identifiers are compared after `unraw()`, so `r#clippy`, `r#debug_assertions`, and `r#cfg` are the same words. The syn walk still checks every nested meta of `cfg_attr`. A plugin has no reason to branch on the build profile or on whether the compiler is Clippy.
- `allow`, `expect`, and `warn` on `clippy::disallowed_*`, `clippy::all`, `clippy::style`, or `clippy::restriction` are rejected, including when they sit inside `cfg_attr`. `clippy::disallowed_types` and `clippy::disallowed_methods` are `clippy::style` lints. `clippy::all` silences them under `-D`.
- Every plugin manifest sets `[lints] workspace = true`. The workspace forbids `unsafe_code`, which is what rejects an FFI block such as `extern "C" { fn system(); }`.
- A plugin must not have a build script. A file named `build.rs` is rejected. `[package] build` is rejected unless it is `false` or the package name is in `BUILD_SCRIPT_ALLOW` in `xtask/src/boundary.rs`. That list is empty. `build = false` does not name a script. The path `build` names, and a root `build.rs`, are scanned for `rustc-cfg` and `rustc-check-cfg` (`cargo:rustc-cfg`, `cargo::rustc-cfg`, and `cargo::rustc-check-cfg`), so a name added to the allow-list later still cannot set a `cfg` that hides code from Clippy.
- `[lib]`, `[[bin]]`, `[[test]]`, `[[example]]`, and `[[bench]]` must not set `path`. `cargo metadata` `targets[].src_path` must be under the package `src/` directory. A target whose root is `tests/`, `examples/`, or `benches/` fails that check. Unit tests inside the library are not a separate target.
- Clippy then runs with `-F clippy::disallowed_types` and `-F clippy::disallowed_methods`, using `xtask/plugin-boundary/clippy.toml`, and `--no-deps`. The host and the kits are not plugin crates: a plugin test may dev-depend on its kit, and that kit's `std::process` is not the plugin's code. `-F` cannot be overridden in source. The config is applied after macro expansion, so `std::$m::Command` is `std::process::Command`. Profiles are `dev` and `release`. A package with no `[features]` is linted once per profile, on the default feature set (`--all-features` and `--no-default-features` compile that same crate). A package that defines features is linted three times per profile: the default set, `--all-features`, and `--no-default-features`. CI runs this step on Linux, macOS, and Windows, so a `cfg` for the host operating system of those runners is compiled.

## Known limits

- This is a review aid. A change that passes the gate can still spawn a process if the author writes ordinary Rust that the lints do not name.
- Clippy compiles the host triple of the CI runner. Arch-specific `cfg` for a target that runner is not building is a known limit. That includes non-dist targets such as `wasm32`, and dist triples the runners do not use (`aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`).
- A `cfg(feature)` that is true only for a combination other than the default set, every feature, or no features is not compiled. The three sets above are the ones the gate lints.
- The source scan does not expand macros. It rejects `cfg` / `cfg_attr` / `cfg!` whose tokens name `clippy` or `debug_assertions`, including raw identifiers, and Clippy sees the expanded splice on the feature sets above. No plugin build script is allow-listed, so none run. An allow-listed script would still be scanned for `rustc-cfg` and would not be macro-expanded.
- A proc-macro already in the API or SDK closure runs at compile time. That is the same trust as the rest of the workspace build.
- String-built command names and calls through function pointers are ordinary Rust. The gate does not try to interpret them.
